# CLAUDE.md

Development guide for every session in this repository. Keep it current: if a
convention changes, update this file in the same change.

## 1. Project overview

Nutri (shown to users as «Mi consulta») is a mobile-first web app (also used
on desktop) for nutritionists to
register patients, their nutrition history and weight/measurement tracking
per consultation. It is multi-clinic: each nutritionist works inside a clinic
and data is isolated per clinic. A read-only portal for patients (or guardians
of minors) is planned. **It handles health data from multiple clinics:
isolation and not leaking data are non-negotiable.**

Design rationale: [docs/architecture.md](docs/architecture.md).

## 2. Language rules

- Code is in **English**: folders, files, identifiers, tables, columns,
  endpoints, comments and tests.
- Commits, README, docs and this file are in **English**.
- The only exception: **user-facing UI text is Spanish**, defined in
  `apps/web/src/i18n/es.ts` with English keys (`t.patients.listTitle`).
  Never hardcode visible strings in components; add a key instead.
- Dates and numbers shown to users go through `apps/web/src/lib/format.ts`
  (`dd/mm/aaaa`, decimal comma). Never format by hand in components.

## 4. Tech stack, commands and layout

Nx + pnpm monorepo, TypeScript 6 (strict). API: NestJS 11, Drizzle ORM,
PostgreSQL, nestjs-zod. Web: React 19, Vite 8, TanStack Router/Query, React
Hook Form, Tailwind CSS 4, shadcn/ui (Base UI), vite-plugin-pwa. Shared: Zod 4.
Tests: Vitest. Exact versions and why some are not the latest major:
"Known technical debt" in docs/architecture.md.

```bash
docker compose up -d            # local PostgreSQL
pnpm dev                        # API (:3000) + web (:4200, proxies /api)
pnpm lint | pnpm typecheck | pnpm test | pnpm build
pnpm nx test api                # one target, one project
pnpm db:generate                # migration from schema changes
pnpm db:migrate                 # apply migrations
pnpm db:seed                    # reset local fictional data
pnpm db:studio
pnpm nx sync                    # after adding a workspace dependency
```

Where things live:

```
apps/api/src/
  config/         env validated with Zod (APP_CONFIG)
  database/       Drizzle client, schema/, migrations/, seed/, testing/
  common/         decorators, guards, filters, request types
  health/         GET /api/health
  auth/           placeholder (TODO)
  modules/<domain>/  module, controller, service, repository, mapper, dto/
apps/web/src/
  app/            providers, query client, router
  routes/         file routes: _clinic/, _auth/, _portal/ layouts
  features/<domain>/  queries (api.ts) and domain components
  components/ui/  shadcn components; components/ generic app components
  i18n/es.ts      all UI text
  lib/            api-client.ts, format.ts, utils.ts
  styles/         globals.css (Tailwind + theme tokens)
libs/shared/schemas   @nutri/schemas: Zod schemas, the API contract
libs/shared/utils     @nutri/utils: pure calculations (BMI, age, diffs)
```

Tooling notes:

- Nx loads the root `.env` into every task. Never put `NODE_ENV` there: it
  leaks into the web production build.
- No `baseUrl` and no `ignoreDeprecations` in any tsconfig. Workspace libs
  are pnpm workspace packages; the web `@/*` alias uses `paths` only.
- `apps/web/src/routeTree.gen.ts` is generated by the router plugin
  (committed, excluded from lint/format). Do not edit it.
- Add shadcn components from `apps/web`: `pnpm dlx shadcn@latest add <name>`.
- Migrations and `routeTree.gen.ts` are excluded from Prettier.

## 5. Architecture rules

- **Backend:** one Nest module per domain; layers controller → service →
  repository.
  - Controllers: HTTP only (routes, DTOs, status codes).
  - Services: business rules; map rows to API shapes (mapper files).
  - Repositories: the only code that touches the database.
- Modules communicate through **exported services**, never through another
  module's repository.
- **Respect Nx module boundaries; never disable
  `@nx/enforce-module-boundaries`.** api and web never import each other;
  shared libs stay framework-free; utils may use schemas, not the reverse.
- **Frontend:** `components/ui` is generic (shadcn); `features/<domain>`
  holds domain logic, queries and components; `routes/` only composes
  features and loads data.
- Forms: shadcn `Field` components + React Hook Form `Controller` +
  `zodResolver` with schemas from `@nutri/schemas`.
- **Styling:** only the design tokens in `styles/globals.css` (Tailwind
  classes such as `bg-primary-soft`, `text-muted-foreground`,
  `rounded-card`). No raw hex values or ad-hoc colors in components; a new
  value is added as a token first. Light-only; controls are at least 44 px
  tall (`min-h-touch`). Import `cn` from `@/lib/utils` (it knows the
  tokens; lint forbids the bare `cn` package). After `shadcn add`, restyle
  the component to the spec and fix its `cn` import.
- Wrap form controls in `FormField` (label, help and error wired by id);
  read typed numbers and dates with `lib/parse.ts`, never by hand.
- Every spec component is shown at `/dev/components` (development only,
  `features/catalog`); add new components there with their variants.

## 6. Multi-tenancy and security (non-negotiable)

- Every access to clinical data is filtered by `clinicId`. Repository
  methods always take `clinicId` and also filter `deleted_at IS NULL`.
- New endpoints go under `/api/clinic/...` (staff, `@ClinicAccess()` +
  `@CurrentClinic()`) or `/api/portal/...` (patients/guardians). The portal
  is read-only and exposes only shareable fields.
- A record from another clinic must behave exactly like a missing one (404).
- Every response uses `@ZodSerializerDto` with a schema from
  `@nutri/schemas`, so undeclared fields (`clinicId`, `deletedAt`) never
  leave the API.
- Clinical records use soft delete (`deleted_at`); never delete physically.
- Never log patient data or secrets (no bodies, no DB error messages, no
  env values).
- Every change that touches clinic isolation ships with a test proving it.
- `DevelopmentClinicGuard` is TEMPORARY (development only) until real auth.
- The service worker must never cache or handle `/api`.

## 7. Data and validation

- Zod schemas in `@nutri/schemas` are the single source of truth. API DTOs
  (`createZodDto`) and web types/validation derive from them; do not
  duplicate shapes.
- snake_case in the database, camelCase in TypeScript (Drizzle
  `casing: 'snake_case'`). Name composite constraints explicitly in
  snake_case.
- Never edit a migration that has been applied; generate a new one.
- Metric units only (kg, m, cm). Timestamps are `timestamptz` in UTC;
  calendar dates are `date` (`YYYY-MM-DD`).
- Every table has uuid `id`, `created_at` and `updated_at`.

## 8. Testing

- **Vitest is the only test runner.** Do not add Jest or other runners.
- Required tests: services, repositories, shared utils and schemas with
  non-trivial rules, and **every clinic-isolation rule**.
- Repository tests run real SQL on PGlite: `createTestDatabase()` and
  fixtures in `apps/api/src/database/testing`.
- Service tests use `Test.createTestingModule` with mocked repositories.
- Naming: `<file>.spec.ts(x)` next to the code; `describe('<Unit>')`;
  `it('<behavior in present tense>')`, e.g.
  `it("cannot read another clinic's patient by id")`.
- API tests are transformed by Oxc, the build by `tsc`; both take decorator
  settings from `apps/api/tsconfig.decorators.json`. After changing tsconfig
  options that affect transforms, run `pnpm exec vitest --clearCache`.

## 9. Git conventions

- Conventional Commits in English, enforced by commitlint:
  `type(scope): subject`. Scope is required, one of
  `api, web, shared, db, infra, docs, deps`.
- Small, atomic commits. The pre-commit hook formats and lints staged files.
- Branches: `feat/...`, `fix/...`, `chore/...` from `main`. (The initial
  scaffold was committed directly to `main`; all further work uses branches.)
- Never commit `.env` or secrets.

## 10. How to add a new feature module

1. **Schema:** add Zod schemas and types in `libs/shared/schemas`
   (response, create, update), with tests for non-trivial rules.
2. **Table:** add the Drizzle table in `apps/api/src/database/schema`
   (`clinic_id`, indexes, soft delete if clinical), export it, then
   `pnpm db:generate` and `pnpm db:migrate`.
3. **Repository:** every method takes `clinicId`; test it on PGlite,
   including isolation between clinics.
4. **Service:** business rules + mapper to the API shape; use other modules
   only through their exported services; test with mocked repositories.
5. **Controller:** under `/api/clinic` (or `/api/portal`), `@ClinicAccess()`,
   DTOs from the shared schemas, `@ZodSerializerDto` on every handler.
6. **Register** the module in `apps/api/src/app.module.ts`.
7. **Web feature:** `features/<domain>/api.ts` (query options with the
   shared schemas) and components.
8. **Routes:** add file routes under the right layout; routes only compose.
9. **Texts:** add every visible string to `i18n/es.ts`.
10. **Tests** for the new web logic; run `pnpm lint typecheck test build`.
11. **Docs:** update docs/architecture.md and this file if an architectural
    rule or convention changed.

## 11. Definition of done

- `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` are green.
  CI (`.github/workflows/ci.yml`) runs them on every pull request to `main`
  for the affected projects only, and on every push to `main` for all of
  them. It caches the pnpm store and `.nx/cache`; editing the workflow
  invalidates every Nx task (it is in `sharedGlobals`).
- No TODO without context (say what, why and when).
- Isolation-sensitive changes include a test proving isolation.
- CLAUDE.md or docs updated if a convention changed; deviations that leave
  work pending are recorded in "Known technical debt".
